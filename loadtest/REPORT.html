Load test & hardening plan · 28 Aug 2026 · branch loadtest · v1.3.1 baseline

Snuffles at 2.8 Mpps

We built a six-container rig on this host, drove snuffles with kernel pktgen, userland floods, SYN floods, HTTP, iperf3 and a 20 k-packet mixed-protocol corpus, profiled every path, and then measured six targeted changes. The capture thread of v1.3.1 saturates one core at about 600 kpps; with the changes it holds 1 M pps with zero loss and tops out near 1.16 Mpps. Four correctness bugs surfaced on the way. Below: what breaks, why, what each fix bought, how established tools do it, and a ranked plan.

The rig

Everything runs in Docker on this machine, pinned so the system under test never shares a core with the traffic sources. The sniffer captures on a Linux bridge inside its own network namespace; four generator containers feed it through veth ports, a sink answers HTTP/iperf3 and counts syslog datagrams over a separate management link so forwarded records are never part of the captured traffic. Host limits were raised (socket buffers, softirq backlog and budget) and are restored by rig.sh down.

Every run records the generator's own counters, the bridge's per-port counters, snuffles' --stats line (a flag added for this work: captured, kernel drops, consumer misses, syslog sent/failed, sessions, RSS) and per-thread CPU from /proc; seven scenarios also carry perf stat and a call-graph profile. Across all 48 baseline scenarios, every frame that entered the bridge was accounted for at the packet socket (seen% = 100), so the kernel-drop counter is the only loss point and the numbers below are app behaviour, not rig loss.

Where v1.3.1 breaks

The capture thread is a single core doing everything per packet: copy, dissect into text, update the session table, then commit to the ring — and that commit did a mutex lock, a condition-variable signal nobody waited on, and a write() to a pipe, for every packet. Ramping the offered rate shows the knee.

What we changed, and what each change bought

Six experiments were implemented as isolated branches, adversarially reviewed, then run alone and combined. On-demand consumer wake-ups are the dominant win; the kernel buffer helps most at rates the app can almost keep up with; output buffering only pays off once the per-packet wake-up is gone (alone, a faster consumer makes the producer's pipe writes succeed more often and costs capture); recvmmsg alone changes nothing because the per-packet work, not the syscall, was the limit.

The experiment branches

  • notify-batch — the ring commit no longer locks a mutex, signals a condvar nothing waits on, or writes to the pipe per packet; the consumer announces when it is about to block and gets exactly one wake-up. Syscalls per packet on the capture thread: 1.0 → 0.
  • pcap-buffer — -B/--buffer-mb (default 64 MB kernel ring instead of libpcap's 2 MB), TPACKET_V3 with 10 ms blocks, pcap_stats() throttled to 4/s, 1024-packet dispatch. Also fixed: -c never stopped a live libpcap capture.
  • consumer-output — 1 MB stdout buffer, one flush per drain batch instead of per line, JSONL built in a stack buffer and written once (byte-identical output, unit-tested).
  • raw-recvmmsg — the no-libpcap backend reads 64 frames per recvmmsg(), sets a 64 MB socket buffer with SO_RCVBUFFORCE, takes kernel timestamps.
  • syslog-nonblock — non-blocking, 32-message sendmmsg() batches, 16 MB send buffer; the capture thread never blocks on the collector.
  • syslog-connect — connect() the UDP socket so each send skips the route lookup the profile showed.

Bugs found while instrumenting

  • bug The raw-socket build's -i used SO_BINDTODEVICE, which AF_PACKET ignores for delivery: -i lo captured every interface (776 foreign vs 40 loopback packets in 3 s). Now binds with sockaddr_ll.
  • bug The libpcap build ignored -c on live capture — -c 20 ran until killed (578 packets).
  • bug The headless printer read records by display index against a floor that moves while it drains: whenever the ring lapped it, output contained duplicates and silently omitted packets while reporting nothing missed. Replaying 200 k unique packets through the default ring printed 143 767 unique lines and 56 233 duplicates; after the fix, 200 000 unique, 0 duplicates.
  • bug (introduced by the new --stats flag, caught by review) gettimeofday without its header broke the Windows cross-build; fixed with a portable clock.

Findings from the multi-lens analysis

Five analysts each took one lens over the raw result files (stats lines, per-thread CPU, bridge counters, perf), and a second set of agents tried to refute every finding by recomputing it. What follows survived; “corrected” means the verifier adjusted a number, which is what is shown.

Capture path

  • The ceiling is a fixed per-packet cost, ~1.6–1.7 µs on one core. Eight different 64-byte scenarios land at 595–622 kpps whatever the interface (bridge or direct veth), delivery path (forwarded or local) or in-kernel BPF (matching everything). The perf stat syscall tracepoints themselves depress the rate 6–12% during their window, so the unperturbed figure is ~615–620 kpps for libpcap and ~430 kpps for the raw-socket build.
  • Bytes are cheap, packets are not. Each extra KB costs ~0.06 µs: 1514 B → −10%, 9014 B → −25%. Cache misses per packet rise 4.4× at 1514 B — the memcpy into a cold 64 KB ring slot, not instructions. Snaplen 128 runs 4% faster at 1/65th the RSS; a 1 M-slot application ring is 8% slower and cannot reduce kernel drops, because the application ring never back-pressures anything — only the capture thread's speed and the kernel buffer control kdrop.
  • Where the time went (v1.3.1, A2): 1.01 syscalls per packet, all snuffles' own — the notify write() plus a getsockopt every 64 packets; roughly a third of the thread is kernel time. pcap_stats() after every 64-packet dispatch makes libpcap open and read a sysfs statistics file ~8 800 times a second, ~5% of the thread by itself.
  • Drop knee: loss-free through 250 kpps; first bursty drops (1.7%) at 500 kpps with the thread at 85%; plateau from 1 M pps up. The bursts at 500 kpps are ~100 ms stalls with no preemption signature, which libpcap's default 2 MB buffer (~2.5 ms of traffic at that rate) cannot absorb — the 64 MB buffer in the experiments is what turns them into latency instead of loss.
  • Flow churn is memory-bound: 1 M sources (A6) cost +122% cycles per packet for +17% instructions; cache misses go from 10 to 153 per packet, IPC 1.76 → 0.93. The table has 4 096 buckets for a 100 000-entry cap (24 entries per chain), compares dotted-quad string keys with strcmp, does two snprintf per packet to normalise the key, and unlinks the LRU victim with a second chain walk. A SYN flood costs the same 3.8 µs per packet, so it is the miss/evict/insert path, not the packet type.
  • RPS onto the sniffer's cores is harmful here: pktgen actually attempted 9.96 Mpps; 81% died at the first backlog enqueue and 77% of the survivors died again at the bridge pass-up, all on the two physical cores snuffles shares. Softirq processing belongs on other cores than the capture thread.
  • Nothing drifts: 5 minutes at 2.8 Mpps offered (845 M frames): captured rate, drop %, RSS, sessions and thread CPU flat from minute 1 to minute 5 while host load doubled. In-kernel BPF that rejects everything leaves the process at 0% CPU and 8.5 MB.

Output paths

  • The mode sets the cap, not the offered load: the ranking is identical at 1 M and 2.8 M pps — quiet › -w /dev/null › jsonl › pipe › TUI ≈ headless › -w disk (1514 B) › syslog › TUI sessions view with 100 k sessions.
  • What was captured was delivered in headless, syslog and -w modes (100%); the pipe consumer delivered 98.3% and jsonl 92.7–98.7% — jsonl's main thread runs at 99% and the 10 000-record ring wraps every ~19 ms at 533 kpps, so any stall laps it. The TUI's own loss is not measurable (it renders what it can).
  • Why jsonl beats plain headless (533 k vs 398 k): not a cheaper consumer — its formatting is more expensive (1.63 vs 1.35 µs per record) — but the headless printer's per-line fflush puts 0.8–1.1 µs of kernel time per record on the consumer and makes the producer's pipe writes succeed instead of failing fast, slowing the capture thread by 25%.
  • Syslog: 4.9 µs per blocking sendto, 71% kernel time, IPC 0.98, 7× the cache misses of quiet mode: route lookup, skb build, and — on a veth — the peer's receive path and the sink's wake-up all run inline on the capture thread. Roughly a quarter of that is a veth artifact a real NIC would not charge.
  • -w to /dev/null costs 6%; to disk at 1514 B it halves the rate — ≈1.4 µs per packet of page-cache copy at ~470 MB/s with the default 4 KB stdio buffer; the 9.4 GB file never left the page cache in 20 s, so the disk itself was not the limit.
  • The TUI renders ~14 000 frames per second under load — the loop re-renders after every wake-up, and one write() of a 200×50 screen per frame puts n_tty_write at a third of the UI thread. The sessions view snapshots the whole table (24 MB, then a 100 k-entry qsort) under the session mutex on every frame, which blocks the capture thread about half the time: capture CPU falls to ~48%, rate halves, and a 1.2%-loss SYN flood becomes 28% loss.
  • Ring wake-ups are paid even with no consumer: one write() per packet in quiet mode (pipe full → EAGAIN, still a full syscall round trip through the SRSO-mitigated entry/exit); with a sleeping consumer it becomes a real wake-up and costs the capture thread another 17–33% at 200 kpps of HTTP.

Sessions and memory

  • RSS is the ring pool, made resident by transparent huge pages. With THP [always], first touch of the 10 000 × 65 535 B pool faults 2 MB pages: 8.5 MB → 647 MB within 0.3 s of the first packet, regardless of packet size, rate or mode. The session table adds 254 B per session (25 MB at the cap) and is flat under churn.
  • The 16 MB reassembly budget is a one-shot pool. 1 024 direction buffers of 16 KB go to the first ~512 sessions that carry TCP payload and are only returned on eviction or clear — there is no release on FIN/RST or idle. In a long-running capture, “Follow stream” finds empty buffers for every connection after the first few hundred.
  • The TUI sessions view keeps a second 23 MB copy of the table (RSS 695 MB vs 672 MB) and re-snapshots it per frame.
  • Fragments create port-0 pseudo-sessions (non-first fragments still go through the session table), though the fragment path itself costs no more per frame than plain UDP of the same size.

Rig validity

  • Frame accounting (bridge in = captured + kernel drops) closes exactly in 45 of 48 scenarios; the three exceptions are explained (A15 BPF reject, A10 RPS backlog drops, C6 a SYN-ACK retransmission burst arriving during shutdown). No softirq backlog drops or time squeezes anywhere except A10.
  • Two rig defects were found by the analysis and fixed: the HTTP Connection: close scenarios had silently run with keep-alive (a jq // true default swallowing false) — re-run below; and udpflood -r only draws from 128 source ports, so it is not a flow-churn test.
  • The replay corpus uses one generator's MAC as source, so a quarter of the “replay” frames the sniffer saw were that generator's kernel answering (RST/ICMP); the SYN flood is amplified 2.3× by the sink's SYN-ACK retransmissions. Both make those scenarios harsher, not gentler.
  • Per-thread context-switch counters in the sampler glitch to zero on single samples (CPU%, RSS and interface counters are sound); host_loadavg mostly measures the rig itself — no scenario's offered rate was depressed by outside load in the baseline run.

How others do it

Five research agents read primary sources (man pages, kernel documentation, project source and docs, papers, engineering blogs) on how libpcap/tcpdump, Wireshark's dumpcap, Suricata, Zeek, Snort 3, DPDK and others reach high packet rates and how they benchmark; a synthesis was then citation-checked page by page (74 URLs fetched, 6 rejected as not supporting the claim and dropped below). Every theme maps directly onto something we measured.

1 · A kernel-shared mmap ring with block-level batching and an explicitly sized buffer

libpcap ≥ 1.5, tcpdump, dumpcap, Suricata and Zeek all read from a PACKET_RX_RING mapped into user space. With TPACKET_V3 the kernel packs variable-size frames into blocks and wakes the reader once per block (the retire timeout is the pcap timeout) — no syscall or wake-up per packet; the kernel documentation claims ~15–20% less CPU and ~2× density over V2. Immediate mode disables that batching and falls back to V2 (tcpdump's FAQ: higher CPU, more loss). The ring size is a first-class knob: libpcap's default is only 2 MiB, tcpdump -B and dumpcap -B expose it, Wireshark's performance page recommends ~20 MB, Suricata configures 100 000 × 1 MiB blocks, Zeek 128 MiB per worker. pcap_stats() is read once a second or at exit, never per read. Sources: packet_mmap, pcap(3), tcpdump FAQ, dumpcap(1), Wireshark Performance, Suricata high-performance config.

→ snuffles: v1.3.1 already used V3 (the immediate-mode #ifdef was dead code) but with the 2 MiB default and a pcap_stats() per 64 packets that opened sysfs files 8 800 times a second. Experiment pcap-buffer applies exactly this practice.

2 · Scale-out is flow-hashed fan-out to shared-nothing workers pinned to cores

Suricata's workers runmode, Zeek clusters and Snort 3 packet threads never hand packets between threads. Each worker owns one AF_PACKET socket in a PACKET_FANOUT group (FANOUT_HASH — a symmetric flow hash keeps both directions of a flow on one worker, in order), runs the whole pipeline and owns its own flow table (Snort: a THREAD_LOCAL flow cache). Threads = RSS queues = cores on the NIC's NUMA node, IRQs pinned, a core or two left for housekeeping. Documented scaling: Snort 3 ~941 kpps per thread → 9.4 Mpps on 10; Suricata ~2 Gbit/s per worker; Cloudflare reached 1.1–1.4 Mpps only after per-thread sockets and NUMA pinning. Sources: Suricata runmodes, packet(7), Zeek cluster setup, libdaq afpacket, Cloudflare, a million packets.

→ snuffles: one capture thread is the structural ceiling (~1.16 Mpps after the experiments). Fan-out with per-worker session tables and rings is the path past the rig's own 2.8 Mpps.

3 · Flow tables key on binary tuples with fast seeded hashes, preallocate entries and cap memory

Suricata's flow key is a packed 24-byte tuple (48 for IPv6), canonicalised by putting the larger address/port in the higher slot, hashed with seeded Jenkins lookup3; buckets are cache-line aligned with a per-bucket lock and flows are expired by a separate manager thread, off the packet path. Flows are preallocated (flow.prealloc) and bounded by a memcap with an emergency mode, because “creating a new flow is a relatively expensive action”. xxHash's small-key benchmark shows FNV among the slowest hashes with poor avalanche. Nobody hashes formatted IP strings. Sources: Suricata flow-hash.c, suricata.yaml, xxHash, DPDK mempool.

→ snuffles: string keys, FNV over strings, strcmp per probe, 4 096 buckets for 100 000 entries, calloc/free per session and an O(chain) eviction — the measured 2.3× slowdown at 1 M flows.

4 · Single-writer lock-free rings: batch on the consumer side, no per-item signalling, right-sized slots

The LMAX Disruptor's central results: with one producer no lock or CAS is needed, and the consumer reads the cursor once and drains everything up to it — 52 ns per hop versus 32 757 ns for a condition-variable queue. Rigtorp's SPSC ring went from 5.5 M to 112 M ops/s by caching the remote index and separating head/tail onto 64-byte lines. DPDK's burst APIs amortise the fixed per-call cost over 32 packets; its mempool pre-allocates fixed objects and forbids malloc on the data path; the mbuf keeps a fixed data area and chains buffers for jumbo frames rather than sizing every slot for the maximum. Suricata's packet slot is sized for MTU+14 with an out-of-line extension for rare big packets — about 2.3 KB, not 64 KB. Sources: Disruptor paper, Rigtorp ring buffer, DPDK mbuf, DPDK efficient code, Suricata decode.h.

→ snuffles: the per-packet mutex+condvar+pipe write was the largest single cost (experiment notify-batch); the 65 535-byte slot is why RSS is 630 MB and why GSO frames are memcpy-bound.

5 · Outputs never run on the packet thread

Zeek buffers log records on the main thread and ships them to a writer thread as one bulk message, flushed on a heartbeat. Suricata writes per-thread EVE files with full stdio buffering and a flush interval; its socket outputs use non-blocking send() and on EAGAIN drop the event and increment a dropped counter rather than stall the packet thread. Thompson's “smart batching”: send immediately when idle, otherwise ship everything that accumulated during the previous send as one I/O. tcpdump's -w is stdio-buffered unless you ask for -U. Sources: Zeek WriterFrontend, Suricata EVE, util-logopenfile.c, Smart batching, tcpdump(1).

→ snuffles: the syslog forwarder blocks the capture thread per datagram (154 kpps); syslog-nonblock + syslog-connect apply the non-blocking/batched half of this practice; a dedicated sender thread is the other half.

6 · Do the minimum per packet: capture-only processes, lazy dissection, filters in the kernel

Wireshark never captures in the GUI: dumpcap only moves bytes from libpcap to disk (a dumpcap→tshark pipe measured 33% loss where dumpcap alone lost nothing). Wireshark dissectors receive a NULL tree when only summary information is needed and must skip string formatting; trees are re-dissected on demand. tshark runs single-pass with -n to avoid name resolution; tcpdump -q/-n print less. Capture filters discard in the kernel before the copy; snaplen MTU+18. Sources: Wireshark capture privileges, README.dissector, tshark(1), Wireshark Performance.

→ snuffles: every packet is formatted into text on the capture thread (~15% of it after the syscalls are gone); the in-kernel BPF path is confirmed free (A15).

7 · Drops are first-class telemetry at every stage, with an explicit target

pcap_stats separates received / dropped by the kernel ring / dropped by the interface; tcpdump prints all three at exit; dumpcap adds its own internal and flushed counters. Suricata exports capture.kernel_packets and capture.kernel_drops per thread every 8 s and states the tuning target — under 1% drops, ideally 0. SEPTun insists on watching every hop (NIC FIFO, softirq backlog, PACKET_STATISTICS) because the application counter only sees the last one; Zeek additionally estimates loss from the traffic itself (ACKs for data it never saw). Sources: pcap_stats(3), dumpcap.c, Suricata statistics, SEPTun, Zeek capture-loss.

→ snuffles: headless modes reported nothing before this work; --stats is the first step and the rig's bridge-side accounting is the SEPTun “every hop” check.

8 · Above ~1 Mpps per core the kernel path is the ceiling; the next step is AF_XDP / netmap / DPDK

Cloudflare measured ~1.4 Mpps per core for the cheapest in-kernel drop (“vanilla Linux can do only about 1 M pps”); netmap showed a raw socket costs ~950 ns per packet against 60–65 cycles with pre-allocated shared rings. AF_XDP (Linux ≥ 4.18) hands NIC frames to user-space rings; on i40e the kernel's own rxdrop benchmark goes 2.9 → 9.6 → 21 Mpps on two cores from SKB to driver-copy to zero-copy. Suricata 7 ships AF_XDP and DPDK runmodes (one socket per RSS queue per worker). Sources: Cloudflare kernel bypass, netmap (ATC '12), AF_XDP, Suricata AF_XDP, LWN on AF_XDP.

→ snuffles: only relevant once fan-out exists and only on a physical NIC — veth has no zero-copy path.

The plan

Ranked by measured or expected gain per unit of effort, with dependencies in order. Items 1–5 exist and are measured (branch exp/all); everything after is sized from the profiles and the practices above. Effort: S ≤ a day, M a few days, L about a week, XL a multi-week structural change.

  1. Ship the six measured experiments and the four bug fixes
    On-demand consumer wake-ups (no mutex/condvar/pipe write per packet); 64 MB kernel ring via -B/--buffer-mb, TPACKET_V3 10 ms blocks, pcap_stats at 4/s, 1 024-packet dispatch; buffered stdout and single-write JSONL; recvmmsg + SO_RCVBUFFORCE for the raw build; non-blocking batched sendmmsg syslog on a connected socket. Measured: capture ceiling 595 k → 1.16 M pps, 1 M pps loss-free, TUI at 1 M pps 60% → 7% drops, syslog 154 k → 255 k. Keep --immediate as an opt-in for low-latency interactive use.

  2. Binary session keys, a properly sized hash table, O(1) eviction, entry pool
    Replace dotted-quad string keys with a packed canonical tuple (larger address/port in the higher slot), a seeded fast hash (xxHash/lookup3 class), buckets ≥ 2× the session cap (power of two, cache-line aligned), doubly linked chains or a back-pointer so LRU eviction stops re-walking a chain, and a preallocated entry free-list instead of calloc/free per flow. Expected: the 1 M-flow case (260 kpps, +122% cycles, 153 cache misses per packet) returns to within ~10–15% of the single-flow ceiling; HTTP connection churn (410 kpps at 100% CPU) and SYN floods follow. Also removes hash-flooding exposure.
    Mpractice 3 · Suricata flow-hash, DPDK mempool
  3. TUI: cap the frame rate and take session snapshots out of the lock
    Render at most ~30 frames/s (today ~14 000/s under load, a third of the UI thread in n_tty_write); snapshot the session table at most every 250 ms, copy only the visible window plus a bounded top-N under the lock, keep one persistent snapshot buffer. Fixes the sessions-view collapse (100 kpps with 1 M flows; 28% loss on a SYN flood that quiet mode captures at 1.2%) and the second 23 MB copy.
    S–Mpractice 6 · no work per packet on the display path
  4. Lazy dissection: binary summary on the hot path, text on demand
    Store addresses, ports, protocol ids and offsets in the record; format src_ip/info/MAC strings only when a consumer displays or exports the record (Wireshark's NULL-tree rule). After item 1, dissect_packet plus libc formatting is the largest user-space cost (~15% of the capture thread); the record shrinks from ~330 B to ~100 B, so the ring touches fewer cache lines. This is the item that moves the single-core ceiling past 1.16 Mpps; syslog CSV formatting moves off the capture thread with item 6.
    Lpractice 6 · Wireshark tree==NULL, tshark -n, tcpdump -q
  5. Variable-size payload arena; mode-aware snaplen; stop copying GSO super-frames whole
    Replace the 10 000 × 65 535 B pool (630 MB resident within 0.3 s under THP) with a packed byte ring or MTU-sized slots plus an out-of-line extension for the rare large frame (Suricata: ~2.3 KB per slot; DPDK mbuf chaining). Default snaplen for quiet/headless/jsonl/-w to MTU+18 unless -s is given; warn when GRO/GSO super-frames (> MTU) are seen. Expected: RSS from ~630 MB to well under 100 MB, iperf-class traffic no longer memcpy-bound (104 kpps at IPC 0.5 → the ~500 kpps of 1514 B frames), and -b 1000000 becomes usable.
    Lpractices 1, 4 · TPACKET_V3 packing, DPDK mbuf, Suricata ext_pkt
  6. Dedicated output threads with bounded queues; sinks that drop and count
    Move syslog, -w and JSONL emission to their own thread(s) fed from the ring, with smart batching (send at once when idle, otherwise everything that accumulated) and explicit per-sink dropped counters instead of stalling capture. Capture stays at the quiet ceiling regardless of the sink; export throughput becomes a per-thread number (≥ 255 kpps per syslog thread from the inline experiment, more with integer formatting). -w to disk gets a large buffer and fdatasync-free writes.
    Lpractice 5 · Zeek writer threads, Suricata EVE, smart batching
  7. Reassembly buffer lifecycle
    Free the 16 KB per-direction stream buffers on FIN/RST and after an idle timeout, keep an LRU over buffer holders, or allocate lazily in 1–4 KB chunks. The through-line: every practice the established tools converge on — batch, never signal per packet; size the kernel buffer; keep outputs and display off the capture thread; key flows on bytes, not strings; copy no more than you must; count drops at every hop — corresponds to a cost we measured in v1.3.1, and the first five items are already implemented and measured on exp/all.

Method & caveats

  • Host is shared (CI runners, KVM guests). Offered rates vary with host load; compare scenarios by drop % at a fixed offered rate rather than by absolute pps. Baseline repeats moved ±10%.
  • veth is packet-bound: pktgen cannot use clone_skb on veth, so each kernel thread offers ~350 kpps and the whole receive path (bridge, tap, copy into the socket ring) is charged to the sender's CPU. The 2.8 Mpps ceiling is the rig's, not a NIC's; against the app's 0.6–1.2 Mpps it is still 2–5× overload.
  • Kernel drops for the libpcap build are read from libpcap's ps_drop (TPACKET ring), which ss does not show; the raw build's socket drops matched the app's counter exactly, and bridge-port accounting confirmed no loss before the socket in any scenario.
  • 30 s windows (20 s for rate sweeps, 300 s soak), trimmed 0.5 s at each end; generators start and stop concurrently.
  • Every number here is in loadtest/results/<run>/summary.md on the branch; the rig is reproducible with loadtest/rig.sh build && rig.sh up && matrix.sh <run> scenarios/*.json.
